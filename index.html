Case Study: ConferenceCycle

A multi-tenant conference platform built on Next.js. Each conference lives on its own subdomain, while organizers manage everything from a single account. Here is how I designed the architecture.

Multi-Tenancy at the Router Level

Built subdomain-aware routing so each conference gets its own isolated data and UI context without duplicating the app. Main app vs tenant detection happens at the edge, not inside pages.

System Design

Server vs. Client Boundary

Layouts, structure, and data fetching stay on the server. Client components are scoped to interactive pieces only, such as forms, modals, and charts. This keeps bundles lean and pages easy to reason about.

Performance

Reusable UI System

Buttons, inputs, tables, and layouts come from one source of truth. Tailwind utility classes stay aligned with consistent design tokens. No one-off pages drift from the system over time.

Component Architecture

Data Layer with TanStack Query

Custom hooks per domain (auth, conference context, attendee lists) keep pages from becoming monoliths. Server state is cached and invalidated predictably, with no waterfall requests.

Data Architecture

Dynamic Theming per Tenant

Conference branding (colors, fonts) is fetched from the API and injected through React context. The same components render correctly for each tenant with no duplicated theme files.

Theming

SEO from the Ground Up

Each public conference page and the marketing site have isolated metadata via Next.js Metadata API. Public routes get SSG/ISR; dynamic organizer pages are server-rendered. Search engines see the right content every time.

SEO
Hardest problem

Routing ambiguity + tenant-aware SEO on conference subdomains

The hardest part was making one Next.js codebase behave like many conference sites, where conferenceName.domain.com always loads the right conference identity, data, and SEO info. I solved this with middleware and host-based routing, then wired the resolved tenant into the conference data flow through context and query keys. This kept pages reusable and handled conference identity once at the edge/request layer, instead of scattering tenant checks across components.

I also implemented tenant-level conference SEO: per-conference metadata generation on [conference] routes (title + description from conferenceName, titleDescription, conferenceDetails), social preview metadata from conference assets, conference-level URL maps from active conference records, and metadata freshness rules when conference details change (dates, name, banner, status).
