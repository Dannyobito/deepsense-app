How I ship under tight deadlines

What I skip, what I do first with Figma, and what actually slows delivery.

Under tight deadlines

What I deliberately skip

Premature abstraction, full design systems too early, unnecessary animations, speculative scalability work, unnecessary libraries, and deep handling for very low-impact edge cases. I ship a clean, responsive, production-ready experience first, then refine from real feedback.

First 1–2 hours with Figma

How I start

Scan all pages for reusable patterns, flag risky or unclear sections early, establish typography and layout rhythm, scaffold routing and layout structure, start with the homepage, and extract reusable components once repetition is obvious. I optimize for momentum and less decision fatigue later.

Timeline reality

What turns 2–3 days into 1–2 weeks

Usually not frontend coding speed. Most delays come from unclear or changing requirements, delayed assets and copy, too many revision rounds before a first version ships, backend or API instability, overengineering simple pages, and perfecting abstractions too early. I prefer shipping a strong first version quickly, then iterating on something real.

Case Study: ConferenceCycle

A multi-tenant conference platform built at Intenttech with Next.js. Each conference lives on its own subdomain, while organizers manage everything from a single account. Here is how I designed the architecture.

Multi-Tenancy at the Router Level

Built subdomain-aware routing so each conference gets its own isolated data and UI context without duplicating the app. Main app vs tenant detection happens at the edge, not inside pages.

System Design

Server vs. Client Boundary

Layouts, structure, and data fetching stay on the server. Client components are scoped to interactive pieces only, such as forms, modals, and charts. This keeps bundles lean and pages easy to reason about.

Rendering Architecture

Reusable UI System

Buttons, inputs, tables, and layouts come from one source of truth. Tailwind utility classes stay aligned with consistent design tokens. No one-off pages drift from the system over time.

Component Architecture

Data Layer with TanStack Query

Custom hooks per domain (auth, conference context, attendee lists) keep pages from becoming monoliths. Server state is cached and invalidated predictably, with no waterfall requests.

Data Architecture

Dynamic Theming per Tenant

Conference branding (colors, fonts) is fetched from the API and injected through React context. The same components render correctly for each tenant with no duplicated theme files.

Theming Architecture

SEO from the Ground Up

Each public conference page and the marketing site have isolated metadata via Next.js Metadata API. Public routes get SSG/ISR; dynamic organizer pages are server-rendered. Search engines see the right content every time.

SEO Architecture

Execution detail

Hardest problem

Routing ambiguity + tenant-aware SEO on conference subdomains

The hardest part was making one Next.js codebase behave like many conference sites, where rasengan-conf.conferencecycle.com always loads the right conference identity, data, and SEO info instead of the main app at conferencecycle.com.

I solved this with middleware and host-based routing, then wired the resolved tenant into conference data flow through context and query keys. This kept pages reusable and handled conference identity once at the edge/request layer.

  • Per-conference metadata generation on conference routes (title + description from conferenceName, titleDescription, conferenceDetails)
  • Conference social preview metadata from conference assets
  • Conference URL maps from active conference records
  • Metadata freshness rules when conference details change (dates, name, banner, status)
